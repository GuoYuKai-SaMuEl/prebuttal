The Prebuttal guide

Prebuttal stress-tests an ML paper before you submit it: a free desk-reject check, then three independent AI reviewers and an area chair on the venue's real review form. This page covers every command and setting, task by task.

1. Install & first run

pip install prebuttal          # or: pipx install prebuttal · uv tool install prebuttal
prebuttal backends             # what you can review with

Python 3.11 or newer. prebuttal backends lists every way to reach a model — agent CLIs you are signed into, API keys, a local Ollama — with the default model of each. If nothing is ready it says the quickest fix, usually a free Gemini key: prebuttal key set gemini.

prebuttal check paper.pdf --venue iclr     # seconds, free, no model
prebuttal run paper.pdf --venue iclr       # the full mock review

A paper can be a PDF, a LaTeX project (a folder, its main .tex, or Overleaf's source .zip from Menu → Download → Source), or an arXiv link or id. LaTeX is read without compiling. Built-in venues: neurips, iclr, icml, acl (ARR) and cvpr — each has a submission checklist page. For anything else, write your own.

2. Before you submit: the desk-reject pre-flight

prebuttal check paper.pdf --venue cvpr      # the PDF you will upload
prebuttal check ./latex-src/ --venue cvpr   # the LaTeX project, without compiling
prebuttal check paper.zip --venue cvpr      # the same, as Overleaf's source .zip

A deterministic check against what gets papers rejected unread — no model, no cost, a few seconds:

  • Anonymity — author names in the PDF metadata, e-mail addresses on page 1, a camera-ready or preprint build of the template, a visible acknowledgements section, links to your own repository, “our previous work [12]”.
  • Format — main-text pages over the venue's limit (two-column layouts included) and missing required sections: the NeurIPS checklist, ICML's impact statement, CVPR's LLM usage statement, ARR's limitations.
  • Leftovers — ?? references, [?] citations, TODOs, and text hidden from human readers.

In a LaTeX project every \ref needs a \label and every \cite a bibliography entry; the page limit needs the compiled PDF. The venue comes from --venue, else prebuttal.toml, else neurips. Limits change every year, so the output names the call each rule came from. Exit code 6 means something can get the paper desk-rejected. Each venue's rules are listed on its page: NeurIPS · ICLR · ICML · ARR · CVPR.

On every push: the GitHub Action

For a paper kept in a GitHub repository, the check runs on every push and pull request. It needs no secrets: nothing is sent anywhere.

# .github/workflows/paper.yml
name: Paper
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: GuoYuKai-SaMuEl/prebuttal@v0.6.0
        with:
          paper: paper/          # a LaTeX folder, main .tex or .zip, or a built PDF
          venue: cvpr            # optional: else prebuttal.toml, else neurips

The job fails on anything that can get the paper desk-rejected; every finding is also an annotation on the run and the pull request.

3. A mock review

prebuttal run paper.pdf --venue iclr
prebuttal run https://arxiv.org/abs/2305.18290 --venue neurips
prebuttal run paper.pdf --dry-run          # the plan and the cost, nothing called

Before calling anything, run prints its plan — which backend and model each reviewer gets and what it may cost — and asks once; -y skips the question, --dry-run stops after it. Then three reviewers read the paper in separate contexts, in parallel, each on the venue's own form, and the area chair writes the meta-review:

RolePersonaReads for
R1senior_kindthe core contribution and the main concerns, constructively
R2adversarialReviewer 2: motivation, baselines, novelty, overclaiming
R3detail_obsessiveevery table cell: statistics, ablations, reproducibility
ACarea_chairweighs the disagreement, estimates the rating, writes the revision plan

Every reviewer has to cite evidence — a section, a table, a number — and reports text that tries to instruct reviewers as a weakness instead of obeying it. On your own draft, run also runs the desk-reject check first: an error becomes the first must of the revision plan and a warning a should, both marked check, and the area chair is told what was found.

Reading the report (sample): the predicted score is the mean of the reviewers, with σ, their spread; a high σ means they disagree, which is worth knowing. The AC's estimate follows, then the revision plan — what to fix first, as must / should / could items with the table or section, the concrete fix and who raised it — and then each full review, labelled with the backend and model that wrote it. Reports land in prebuttal-reports/<project>/<date>_<venue>/ as Markdown and HTML, with latest.md / latest.html beside them and a .gitignore so reviews of unpublished work stay out of version control.

Per-run flags: --venue, --backend and --model (one backend or model for every role), --project, --note, --no-save, -c (a config file), --dry-run and -y. Everything that holds for the whole paper lives in prebuttal.toml.

4. The revision loop

Revise, then run again with a note on what changed:

prebuttal run paper.pdf --note "added the Perceiver baseline"
prebuttal diff          # newest run vs the one before: ratings, weaknesses, plan items
prebuttal diff --llm    # match plan items by meaning (one model call) instead of wording

diff lists the plan items that are no longer raised, the ones still raised, and what is new. Plain diff matches by wording, so a reworded issue can show up as both “not re-detected” and “new” — read both lists before ticking anything off, or use --llm. The seed stays the same between runs unless you change seed in prebuttal.toml.

Single runs are noisy: a score that moves by a point may be the model, not your revision. The Mamba revision demo shows what that looks like on a real paper.

A reviewer failed (a quota, a timeout)? The report uses the reviews that finished, and prebuttal retry re-runs only the failed reviewers and the AC, on the same text. Ctrl+C keeps what finished, too.

5. Projects & history

Each paper is a project, found from its source: the same PDF or .zip path, LaTeX folder or arXiv id always lands in the same project, even after a title change — and so does a re-download saved as paper (1).zip. --project NAME picks one yourself. Every run is archived under ~/.prebuttal/ (user-only; --no-save opts out) and numbered, so these work from any folder:

prebuttal projects                   # one line per paper: runs, latest score, trend
prebuttal projects --open            # the same as an offline HTML overview
prebuttal runs mamba                 # a paper's runs, newest first, with notes
prebuttal show                       # print the newest report
prebuttal show mamba#3 --open        # open one in the browser
prebuttal show -o review.html        # save a copy (.md, .html or .json)
prebuttal show --plan                # only the revision plan, as a checklist
prebuttal show --json                # the stored report.json
prebuttal note mamba#3 "after the ablation"
prebuttal rm mamba#2                 # delete a run (a whole paper: projects rm)
prebuttal projects rename mamba mamba-v2

A run is latest (the default), mamba (a project's newest run), mamba#3, mamba~1 (one before the newest) or an id prefix. rm wants a specific run, so a project name alone is refused there.

6. Backends & privacy

With backend = "auto" (the default) the reviewers get different ready backends in this order of preference — cycling when fewer are ready — and the AC gets the first. With both agent CLIs signed in, that is a cross-model panel at no API cost:

BackendAccessNotes
agent-claudeyour Claude subscription, no API keyruns claude -p with no tools at all
agent-codexyour Codex subscription, no API keyruns codex exec with no shell or file access
api-geminiGEMINI_API_KEYfree tier — the cheapest first key
api-openai / api-anthropicOPENAI_API_KEY / ANTHROPIC_API_KEYmid-tier models by default
api-openrouterOPENROUTER_API_KEYhundreds of models; :free ids cost nothing
ollamanonelocal: the paper never leaves your machine
relaynoneprompts go to files and you or your agent answer; never chosen automatically

An agent CLI counts only when it is signed in (asked through claude auth status / codex login status, no model call). Ollama's default is the first installed model that can chat; embedding models are skipped. prebuttal backends <name> lists one backend's models.

Keys. prebuttal key set gemini asks for the key with hidden input and stores it in ~/.prebuttal/keys.env (user-only); real environment variables win. prebuttal backends shows which keys are set, masked; prebuttal key unset gemini removes one. Keys never appear in reports, are never passed to agent CLIs, and the agent CLIs get no tool that could read the file.

Unpublished paper? Its text goes to the backend's provider (OpenRouter passes it on to an upstream one), and what happens there is that provider's policy. Free tiers are usually paid for with your data (logging, training): fine for published papers and for trying the tool; for unpublished work check the terms, use a paid tier, or stay local with ollama or relay. Prebuttal runs no servers and sends no telemetry. Reports quote your paper, so sharing a report publishes those excerpts.
Environment variablePurpose
GEMINI_API_KEY (or GOOGLE_API_KEY), OPENAI_API_KEY, ANTHROPIC_API_KEY, OPENROUTER_API_KEYenable the matching API backend
OPENAI_BASE_URLpoint api-openai at an OpenAI-compatible proxy
PREBUTTAL_OPENAI_MODEL, …_ANTHROPIC_MODEL, …_GEMINI_MODEL, …_OPENROUTER_MODELoverride a backend's default model
PREBUTTAL_OLLAMA_HOST (or OLLAMA_HOST)the Ollama address, default http://localhost:11434
PREBUTTAL_BACKENDone backend for every role, e.g. relay; --backend still wins

7. Configuration: prebuttal.toml

prebuttal init writes a commented prebuttal.toml in the current folder; run and check pick it up from there, or from -c PATH. A typical setup pins one model per reviewer:

[default]
venue = "iclr"
seed = 42

[[reviewer]]
id = "R1"
persona = "senior_kind"
backend = "agent-claude"      # claude -p, subscription
model = "sonnet"

[[reviewer]]
id = "R2"
persona = "adversarial"
backend = "agent-codex"       # codex exec, subscription

[[reviewer]]
id = "R3"
persona = "detail_obsessive"
backend = "api-gemini"        # free tier

[ac]
backend = "agent-claude"
model = "opus"

--backend and --model override the file for one run; every role then uses that backend's default model unless --model is given. A prebuttal.toml found in the current folder — say, inside a co-author's repository — can't run commands, pick a provider or write outside the folder without asking you first; pass it with -c to trust it.

Reasoning effort

Leave effort unset and every model thinks as much as its provider's default — right for most papers. Set it to trade cost and time for depth; each backend gets its own control:

BackendSent as
agent-claudeclaude --effort
agent-codex-c model_reasoning_effort=...
api-anthropicoutput_config.effort
api-openaireasoning_effort (gpt-5 and later, o-series)
api-geminithinkingLevel (Gemini 3+) / thinkingBudget (2.x)
api-openrouterreasoning.effort
ollamathink (gpt-oss models)

Where a model has no such control the setting is skipped; --dry-run says so up front, and every report lists the effort each review actually ran with.

Figures as images

Reviewers read figure captions. With figures = true, reviewers on the vision-capable API backends also see the figures: for a PDF or arXiv paper, each page holding a figure caption; for a LaTeX project, the first \includegraphics of each figure (files inside the project only). A text-only model is retried without images; agent CLIs, Ollama and relay keep the captions.

8. Your own venue

AAAI, KDD, a journal, this year's revised form, your lab's mock review — any venue is one TOML file plus the form text reviewers read:

prebuttal venues                                   # every form, built-in and yours
prebuttal venues cvpr                              # one venue: its scores and form
prebuttal venues new aaai                          # a template in ~/.prebuttal/venues/
prebuttal venues new icml-2027 --from icml --here  # copy a built-in, project-local
prebuttal run paper.pdf --venue aaai               # or --venue path/to/venue.toml
# aaai.toml
name = "AAAI 2027"
form = "aaai.md"          # the reviewer guidelines, shown to reviewers verbatim
rating = "rating"         # which score is the overall recommendation

[[fields]]
key = "weaknesses"
label = "Weaknesses"
kind = "list"             # text | list | score

[[fields]]
key = "rating"
label = "Overall recommendation"
kind = "score"
max = 6                   # scores run 1..max; half_steps = true allows 3.5
anchors = { "1" = "Reject", "3" = "Borderline", "6" = "Strong accept" }

[checks]                  # optional: what `prebuttal check` holds it to
double_blind = true
page_limit = 8
required_sections = ["Limitations"]   # these don't count toward the limit

Venues are looked up in ./.prebuttal/venues/ (commit it for co-authors), then ~/.prebuttal/venues/; built-in names can't be shadowed. Files are validated before any model is called, and reports keep the venue's definition, so archived runs still render after the file changes. A form is instructions to your reviewers: only use venue files you trust.

9. Inside a coding agent

The agent skill teaches Claude Code, Codex or any other agent to drive the CLI and read its JSON. Its one hard rule: the agent runs the CLI, and never role-plays the reviewers itself.

mkdir -p ~/.claude/skills/prebuttal && curl -fsSL -o ~/.claude/skills/prebuttal/SKILL.md \
  https://raw.githubusercontent.com/GuoYuKai-SaMuEl/prebuttal/main/skills/prebuttal/SKILL.md

Other agents: copy skills/prebuttal/ wherever yours discovers skills, or reference the file from AGENTS.md.

Relay needs no key and no CLI login: prebuttal run --backend relay writes each reviewer's prompt to a file and waits; the agent's subagents — or you, or any other system — write the answers next to them, and the run continues. The CLI must run in the background while the agent answers, which is why relay is never picked automatically; PREBUTTAL_BACKEND=relay pins it for a whole environment. Inside Claude Code or Gemini CLI, prebuttal run and prebuttal backends print a one-line relay hint.

10. Command reference

Generated from the CLI itself; prebuttal <command> -h prints the same. Exit codes: 0 success · 2 bad usage, config or paper · 3 no backend available · 4 some reviewers or the AC failed (report written; prebuttal retry) · 5 every reviewer failed · 6 check found a desk-reject problem · 130 interrupted (finished reviews are kept).

prebuttal run

review a paper (PDF / LaTeX dir or .zip / arXiv link)

prebuttal run [--venue VENUE] [-c CONFIG] [--backend BACKEND] [--model MODEL] [--dry-run] [-y] [--project PROJECT] [--note NOTE] [--no-save] paper
paperpath to .pdf, LaTeX project (dir, .tex or .zip), or arXiv link/id
--venue VENUEreview form: neurips, iclr, icml, acl, cvpr, a custom venue name, or a venue .toml file (see prebuttal venues)
-c, --config CONFIGprebuttal.toml path
--backend BACKENDforce a backend for all roles
--model MODELforce a model id for all roles
--dry-runshow cost + backends, call nothing
-y, --yesskip the plan confirmation prompt (auto mode; non-interactive never prompts). A prebuttal.toml found in this folder still asks once — pass it with -c to skip
--project PROJECTproject name (default: one per paper — the same path / arXiv id lands in the same project, named after the title)
--note NOTEwhat changed in this revision, e.g. "added ablation"
--no-savedo not archive this run to the run history (~/.prebuttal, or $PREBUTTAL_HOME)

prebuttal retry

re-run only the failed reviewers of a run, then the AC (default: latest)

prebuttal retry [run]
runa run: name#3, name~1 (one before the newest) or an id prefix (default: latest)

prebuttal check

desk-reject pre-flight: anonymity, page limit, required sections, ?? — no model

paperpath to .pdf, LaTeX project (dir, .tex or .zip), or arXiv link/id
--venue VENUEwhose rules to check against (as for run; default: prebuttal.toml, else neurips)

prebuttal backends [backend]

--forceoverwrite existing file

11. What the scores mean

Prebuttal is a stress test, not a prediction. It shows what a skeptical, careful reader is likely to raise, so you can fix it before real reviewers see it. It does not tell you whether the paper will be accepted:

  • Single runs are noisy. On the Mamba demo the score did not move between the rejected and the revised version once three seeds were averaged; a single-run 7.0 → 7.3 had looked like progress.
  • Models know famous papers. Published papers are in the models' training data, which pushes their scores up.
  • Scores are not calibrated yet. A calibration script against real OpenReview ratings exists; no results are published.
  • Disagreement is information. Every aggregate comes with σ, and every review with the backend and model that wrote it.

Mind each venue's policy: using AI to prepare your own paper is yours to decide; using it to review someone else's must follow that venue's rules.
