Answer Reviewer 2 before Reviewer 2 exists.

Prebuttal is a pre-submission stress test for ML papers: three AI reviewers with different temperaments — running in fully independent contexts — plus an area chair, delivering a conference-format review report before the real Reviewers 1–3 see your manuscript.

pip install prebuttal
▶ See a sample report GitHub

Why not just paste the paper into a chatbot?

One conversation role-playing three reviewers collapses into one bland compromise opinion.

Three reviewers, zero shared context

Each reviewer is a separate call or process with its own persona and model — verdicts genuinely differ, and the disagreement (σ) is reported, always.

Real review forms

NeurIPS 1–6, ICLR 1–10, ICML 1–10 and ARR Soundness/Excitement/Overall — with the official scale anchors, not invented ones. Another venue? Any form and scale is one TOML file: prebuttal venues new cvpr.

Cell-accurate ingestion

LaTeX parsing, PDF table extraction with per-cell geometry, caption fallback — reviewers cite your “Table 3, column 4”, not a guess.

Honest by construction

Every review is labeled with its backend and model; a calibration script measures scores against real OpenReview ratings (results not yet published); run history diffs weaknesses across revisions.

Sample runs

Full runs on public arXiv papers, compared with their real OpenReview outcomes. Unofficial demos — not written or endorsed by the papers' authors.

Calibration caveats, stated plainly: frontier models have almost certainly seen these papers in training (contamination), which pushes scores toward the lenient side — an earlier single-model panel rated Mamba 8/8/8 with no dissenter at all. The revision-round demo above shows a directionally-correct but modest response. These comparisons illustrate the workflow, not a validated predictor. A stress test, not a prophecy.

The revision loop

Every run ends with a prioritised revision plan; every paper is a project whose runs line up as revision history — and two runs can be diffed.

# abridged output of the real runs
$ prebuttal run 2312.00752v1 --project mamba-revision --note "v1 — rejected at ICLR 2024"
  R1 claude/sonnet 8 · R2 codex 5 · R3 gemini-3.8-flash 8
  Predicted: 7/10 (σ 1.41)          → saved as mamba-revision#1

$ prebuttal run 2312.00752 --note "v2 — revised, accepted at COLM 2024"
  Predicted: 7.33/10 (σ 0.94)       → saved as mamba-revision#2

$ prebuttal diff
  panel        7/10 → 7.33/10   (Δ +0.33) · σ 1.41 → 0.94
  adversarial  5 → 6            (Δ +1)
  gone:        "Mamba-3B vs 2.8B naming inconsistency"   — fixed by the revision
  persists:    "no variance / error bars reported"       — the real reviewers' complaint too

A revision plan, not just a verdict

The area chair merges what the reviewers raised into a short checklist — must / should / could, the issue with its table or section, the concrete fix, who raised it. prebuttal plan prints it; the next prebuttal diff checks it against the re-run. New in v0.3.

Projects & run history

Each paper gets a project found from its source — the same PDF, LaTeX folder or arXiv id always lands in the same project, even after a title change. Runs are numbered (mamba#3) and carry your --note "what changed".

A local dashboard

prebuttal dashboard writes one offline HTML page with every project, score trends and links to each report — no server, no network, nothing leaves your machine. The archive itself is user-only (0700).

Reports that never overwrite

Every run writes its own folder — prebuttal-reports/<project>/<date>_<venue>/ — plus latest.md / latest.html, with a built-in .gitignore so reviews of unpublished work stay out of version control.

Bring your own backend

Auto-detected at startup; every run records who reviewed what.

Privacy: your paper’s text goes to the backend’s provider — what happens there is that provider’s privacy policy, not this tool’s. Prebuttal is an integration layer, not a data custodian. For unpublished work use ollama or relay.
